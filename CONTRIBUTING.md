# Contributing to IOU

Keep the workflow lightweight: small branches, clear contracts, and reviewed PRs.
The initial bootstrap commit establishes `main`; after that, do not push directly
to `main`.

## Branches

Start from current `main` and use a short-lived branch for one coherent change:

```sh
git switch main
git pull --ff-only
git switch -c feat/loan-tracking
```

Prefixes: `feat/`, `fix/`, `docs/`, `chore/`, `test/`, `refactor/`, `ci/`.
Examples: `fix/interest-rounding`, `docs/local-setup`.

Open a draft PR early if another teammate needs your API or schema. Agree on request/
response shapes and calculation rules before independently building both sides.
Avoid unrelated cleanups and dependency churn in feature PRs.

## Conventional Commits

Use [Conventional Commits 1.0](https://www.conventionalcommits.org/en/v1.0.0/):

```text
<type>[optional scope][!]: <description>
```

```text
feat(loans): add repayment endpoint
fix(fees): stop accrual after settlement
docs: explain database setup
chore: refresh Python dependency locks
feat(api)!: rename borrower identifier
```

Types: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`,
`chore`, `revert`. Optional scopes describe a subsystem, such as `loans`, `friends`,
`reminders`, `scores`, or `api`. Describe the change clearly; keep the subject short.
`style` means formatting, not a new UI feature. Breaking changes use `!` and/or a
`BREAKING CHANGE:` footer explaining the migration.

PR titles use the same format: **the title becomes the squash commit message**.
CI checks titles on PR creation, edits, and updates. Local hooks are not required.
Before merging, remove noisy temporary commit messages from the squash body.

## Pull requests and reviews

1. Implement one focused change and add appropriate tests.
2. Run `make check`; run `make test-db` when database code/migrations change.
3. Push your branch and open a PR against `main`; fill out the template.
4. Explain manual testing and attach screenshots for visible UI changes.
5. Request at least one teammate review, address feedback, and resolve discussions.
6. Wait for required checks, **squash merge**, then delete the branch.
7. Pull updated `main` before starting your next task.

If `main` changes while you work, merge it into your branch or rebase a branch only
you own. If a rebase needs a force push, use `--force-with-lease`; never force push
`main` or rewrite another teammate's work without agreement.

## Code and data practices

- React stays JavaScript/JSX for now. Use functional components and existing ESLint rules.
- Python uses type hints and Ruff formatting/linting. Keep HTTP handling, persistence,
  and future fee/scoring calculations separated and independently testable.
- New endpoints validate inputs; future owner-scoped queries enforce ownership server-side.
- Never use floating-point arithmetic for money. See provisional rules in `docs/SPEC.md`.
- Model changes require a reviewed Alembic migration in the same PR. Import new model
  modules in `backend/migrations/env.py`; never run `create_all()` at app startup.
- Autogenerated migrations are drafts: inspect operations, test on a disposable database,
  and document destructive changes and rollback limitations.
- Coordinate migration branches to avoid multiple heads; resolve with a reviewed merge
  revision rather than rewriting already-applied shared migrations.
- Edit Python `requirements*.in`, then `make lock`; commit both source files and generated
  locks. `requirements-dev.txt` includes the complete runtime constrained to its lock.
- Use npm to update frontend dependencies and commit `package-lock.json`.
- Document new configuration in `.env.example` and setup docs. Backend secrets never
  belong in `VITE_*` variables (those are public browser bundle values).
- Never commit `.env`, database files, real borrower data, email contents, or credentials.
  If a secret is exposed, revoke/rotate it; deleting the file is not enough.

## GitHub setup (repository maintainer)

After creating and pushing the empty `informal-obligations-utility` repository:

- Set `main` as the default branch and invite teammates.
- Allow squash merging; use the PR title as the default squash message.
- Disable merge commits/rebase merging for a consistent workflow.
- Enable automatic deletion of merged branches.
- Protect `main` (or add a ruleset): require PRs, one approval, resolved conversations,
  passing **Frontend**, **Backend**, and **Conventional PR title** checks; block force
  pushes and deletion. Enable the protections for administrators where practical.
- Enable Actions and run the first CI workflow so its check names become selectable.
- Require an up-to-date branch before merge if it does not become a hackathon bottleneck.

These settings are configured on GitHub, not enforced by files in this repository.
The bootstrap push is the only direct-to-main exception.
